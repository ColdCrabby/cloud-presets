# API Surface

The HTTP contract: what the cloud serves, to whom, and how clients cache it.

The API is described by **OpenAPI 3.1**, generated by Huma from the Go request
and response types. The spec is written to a file at build time and is the input
to the Angular client generator, so the frontends cannot drift from the server.

Preset field semantics are in [preset-schema.md](./preset-schema.md); auth is in
[vendor-workflow.md](./vendor-workflow.md).

## Consumers

Three clients with genuinely different needs, served by one catalog:

| Consumer | Needs | Auth |
| --- | --- | --- |
| **Public app** | Paginated fuzzy search, filters, preset detail | None |
| **Slicer** | Whole categories in one call, to cache in memory | None for reads; Connected Apps token for hand-off |
| **Vendor Admin** | Vendor-scoped reads, validation, PR creation | Stytch session JWT |

The public app and the slicer want **different shapes of the same data**, which
is why both search and bulk endpoints exist. See
[Slicer Bulk Endpoints](#slicer-bulk-endpoints) for why this is not redundancy.

---

## Versioning and Base Path

All endpoints are under `/v1`. This is the **API** version and is independent of
the **preset schema** version — the two change for different reasons and are
allowed to move separately.

Backwards-compatible additions (a new optional query parameter, a new response
field) happen in place. A `/v2` is introduced only for breaking changes, and
`/v1` continues to serve while clients migrate. The slicer in particular ships in
desktop builds that may not update for a long time.

## Catalog Revision and Caching

Every response is derived from exactly one Git commit. That commit SHA is the
**catalog revision**, and it is the basis for all caching:

- Responses carry `X-Catalog-Revision: <sha>`.
- Cacheable responses carry a strong `ETag`. The ETag is derived from the catalog
  revision **and the server build identity** — the schema digest, the validator
  digest, and the search-ranking version — plus the request itself.

Including the build identity is not optional bookkeeping. The revision alone
identifies the *input* commit, not the *representation*: change the serialisation,
the ranking, or the canonical URL configuration, and the bytes change while the
commit does not. An ETag keyed only on the revision would then serve stale
representations indefinitely, which is precisely the failure that "exact rather
than heuristic" caching is supposed to rule out.

Because the catalog only changes on ingest, and the build identity only changes
on deploy, this is exact rather than expiry-guessing. Clients revalidate with
`If-None-Match` and receive `304 Not Modified` while both are unchanged. Note
that revalidation is still a *pull*: nothing notifies a client that ingest
happened, so a client that never revalidates can hold stale data for as long as
it likes.

Exposing the revision also makes staleness **observable**. If ingest starts
failing, the API keeps serving the last good catalog; without a visible revision,
that silent freeze would be undetectable from the outside.

## Public Endpoints

### Search

```http
GET /v1/presets?q=mk4&type=printer&vendor=prusa&limit=20&cursor=...
```

| Parameter | Meaning |
| --- | --- |
| `q` | Fuzzy query across name, vendor, model, material. Omit to browse. |
| `type` | `printer` \| `filament` \| `process` |
| `vendor` | Exact vendor slug filter |
| `material` | Filament material family (`PLA`, `PETG`, …) |
| `limit` | Page size, bounded server-side |
| `cursor` | Opaque continuation token |

Results are ranked by fuzzy score when `q` is present. Each result reports **the
field that matched and the matched ranges within it**, so the frontend can
highlight the substring that caused the match. Returning this from the server
avoids every client re-implementing the same highlighting against a different
matcher, and guarantees the highlight reflects the ranking actually applied.

Ranges are expressed as **UTF-16 code-unit offsets into the original,
unnormalised field value**. This is spelled out because it is a real trap: Go
indexes strings by byte, JavaScript by UTF-16 code unit, and matching itself runs
over case-folded, Unicode-normalised text. A range computed in any of those other
coordinate systems will silently misplace highlights on any vendor or material
name outside ASCII. Matching is case-insensitive and normalisation-insensitive;
ties are broken deterministically so equal scores do not reorder between
identical requests.

Responses are **summaries**, not whole presets — enough to render a result row
(id, type, name, vendor, model or material, a short spec string) without shipping
92 slicing parameters per row.

Pagination is **cursor-based**. A cursor encodes the revision and build identity
it was issued against; presenting it after either changes returns `409` rather
than silently paginating across two different catalogs. Only the current catalog
is retained, so an old cursor cannot be honoured — failing loudly is the only
correct option.

### Detail

```http
GET /v1/presets/{id}
```

Returns the complete preset in the slicer's profile shape, with `source` set to
`catalog` and `import_url` set to this preset's canonical URL. This is the exact
JSON the slicer can consume directly.

This is the **only** way to obtain a full preset: search returns summaries, so a
client imports one specific preset by fetching it here rather than downloading
the whole catalog and filtering locally. A well-formed id that names no preset
returns **`404 Not Found`**.

Retired presets return **`410 Gone`**, optionally naming a successor, so a client
can distinguish "withdrawn" from "never existed". IDs are never reused, so `410`
is permanent.

### Download

```http
GET /v1/presets/{id}/download
```

The preset as YAML, with `Content-Disposition` set, for users who want the file
itself. Content negotiation serves JSON for `Accept: application/json`.

### Vendors

```http
GET /v1/vendors?limit=20&cursor=...
GET /v1/vendors/{slug}
```

The vendor directory, derived from the `vendor.yaml` manifests. Includes slug,
display name, brands, and website. `stytch_organization_id` is **not** part of
the public representation — not because it is secret (it sits in a public
repository), but because it is an authorization detail with no meaning to API
consumers.

Like search, the directory is **cursor-paginated** (ordered by slug) and never
returned as one unbounded array, so no endpoint dumps the whole set in a single
response. Cursors carry the same revision/build binding as search and return
`409` when stale.

## Slicer Integration

The slicer does **not** get bulk "dump everything" endpoints. There is no
`GET /v1/catalog/printers` (or `/filaments`, `/processes`) returning a complete
array of full presets: an endpoint that ships the entire catalog in one response
is explicitly disallowed, because it grows unbounded with the catalog and forces
every consumer to download and filter everything to find one preset.

Instead the slicer integrates through the two bounded endpoints above:

- **Browse/search** with `GET /v1/presets` — always paged, summaries only.
- **Import one preset** with `GET /v1/presets/{id}` — the full profile in the
  slicer's shape, fetched only for the preset the user actually selected.

The slicer's adapter walks pages via the cursor to populate its `CatalogSource`
lazily rather than fetching everything once. Because pages change only per
revision, `ETag`/`304` handling still applies per page.

Because the slicer is a browser app served from its own origin
(`https://slicer.maxsopp.de`), the API answers its requests with cross-origin
resource sharing (CORS) headers. The allowlist defaults to that origin and is
overridable with the comma-separated `CORS_ALLOWED_ORIGINS` env var; requests
without an `Origin`, or from an origin not on the list, are served unchanged
(same-origin and non-browser callers are unaffected).

Note the naming mismatch: the slicer calls the quality category `profiles()` in
its interface, while the engine, the repository, and this API all call it
**processes**. The API uses `processes` consistently; the adapter on the slicer
side absorbs the difference.

## Vendor Endpoints

Every endpoint in this section requires a valid Stytch session JWT and is scoped
to the caller's organization. Authorization is described in
[vendor-workflow.md](./vendor-workflow.md). The slicer hand-off endpoint is
**not** in this group — it has its own contract, described in
[Slicer Hand-Off](#slicer-hand-off).

Writes authorize against the manifest at the **current `main`**, not at the
served catalog revision, and fail closed if the head cannot be resolved. The
served catalog is allowed to lag; ownership must not.

### Scoped listing

```http
GET /v1/vendor/presets
```

The presets the caller's organization owns, resolved from its vendor manifest.
Never a filter over the public catalog — the server derives the scope from the
JWT's organization claim, so a client cannot widen it by changing a parameter.

### Validation (dry run)

```http
POST /v1/vendor/presets/validate
```

Validates a candidate preset and returns structured field-level errors. Nothing
is written.

The request carries the **target path and a base revision**, because validation
is not purely per-file: ID uniqueness and path ownership are cross-file checks
that only mean something against a specific catalog state. Without them the
endpoint could only answer the schema half of the question, and would report a
duplicate ID as valid.

It runs the same code and the same pinned schemas as CI and ingest, so a dry run
that passes against the current head is a genuine prediction rather than an
approximation.

### Propose a change

```http
POST /v1/vendor/changes
GET  /v1/vendor/changes/{id}
```

Submits a change set (created, updated, or deleted presets) for the caller's
vendor. The server validates it, then the GitHub App bot creates a branch,
commits the YAML, and opens a pull request. The response carries the pull request
URL.

**Submissions are idempotent.** GitHub cannot atomically create a commit and a
pull request, so a timeout can leave a branch with no PR, or a PR the client
never learned about — and a naive retry would then open a duplicate. Each
submission therefore carries an **idempotency key** derived from the change
content, which maps to a deterministic branch name. Retrying re-drives the same
branch: an existing branch is reused, an existing PR is returned as-is, and an
orphaned branch is completed rather than duplicated. Recovery reads state from
GitHub rather than from server memory, so it survives a restart.

The change set is **not** stored server-side beyond the request: the pull request
*is* the record. `GET` reads the current state back from the GitHub API. This
keeps the no-database property intact — there is no queue of pending changes to
persist, reconcile, or lose.

Because every write becomes a PR, these endpoints are inherently
**write-behind**: a successful call means "a pull request now exists", never "the
catalog changed". The catalog changes when the PR is merged and ingest runs.

Upstream GitHub failures surface as `502` (GitHub rejected or was unreachable)
or `503` with `Retry-After` when the App's rate limit is exhausted — never as a
success the client would have to reconcile later.

### Manual upload and claim

```http
POST /v1/uploads                 # park uploaded preset files (public)
GET  /v1/uploads/{id}            # read a parked draft for review (public)
POST /v1/uploads/{id}/claim      # authorize + open a PR for the draft (Stytch JWT)
```

For vendors who already have preset files — a `.zip` exported elsewhere, or a
handful of YAML files — this is the manual equivalent of the slicer hand-off.
The shape is the same **upload, then claim** flow: park the files under an
unguessable id, then let the admin app load them back to review and submit.

`POST /v1/uploads` accepts a multipart form (`files`) carrying either a `.zip`
laid out like the repository (`printers/…`, `filaments/…`, `processes/…`) or
individual preset files. A bare file's kind comes from its name (a `printers/`
or `filaments/` path) or the `type` query parameter; a zip's kind comes from
each entry's path. Every file is validated against the **same pinned schemas**
as CI and ingest before it is parked, so an invalid upload fails fast with
structured, per-file errors rather than being discovered at claim time. On
success the endpoint returns the draft id, the parsed files, and a `claimUrl`
into the admin app.

The parked draft is **ephemeral, in-memory, and TTL-bounded**: it is not a
database, it does not survive a restart, and it is dropped after roughly half an
hour. It is the transient carrier of a hand-off, nothing more.

`GET /v1/uploads/{id}` returns the draft for review. Like the hand-off token, the
id **authorizes nothing** — it only lets the admin app render the files.

`POST /v1/uploads/{id}/claim` is where authority is checked. It requires a Stytch
session JWT, resolves the caller's writable vendor slug from the `vendor.yaml`
manifest at the current head (a `403` when the organization owns no namespace),
places each file at `vendors/<slug>/<printers|filaments>/<id>.yaml` so a vendor
can never write outside its own directory, and opens a pull request through the
bot exactly as [Propose a change](#propose-a-change) does — same idempotent,
content-derived branch, same provenance trailer. Process presets are rejected: the
shared `processes/` namespace is not writable through the API. Claiming consumes
the draft. When the bot is not configured (local dev), the claim still resolves
and validates the change set and reports the target paths, but opens no pull
request.

Unlike the slicer hand-off, all three are ordinary typed operations in the
OpenAPI document, so the frontends call them through the generated client. The
claim's Stytch requirement is enforced by the same offline JWT validation as the
other vendor endpoints, applied as operation middleware rather than a wrapping
handler.

## Slicer Hand-Off

```http
POST /v1/sync/handoff
```

Accepts slicer-side profile state and returns a short-lived token plus a Vendor
Admin URL. It is listed separately because it does **not** take a Stytch session
JWT: the caller is the slicer, authenticated as a public OAuth client through
Stytch Connected Apps, and Connected Apps access tokens are a different credential
from first-party session JWTs.

The hand-off token is **self-contained** — signed, encrypted, short-lived, and
carrying the draft state itself. It is not a server-side handle, because storing
draft state would reintroduce the database this design does not have.

The token authorizes nothing on its own. It only lets Vendor Admin load the
draft; creating the pull request still requires a normal authenticated session
and a fresh ownership check. Replaying a hand-off token therefore achieves
nothing beyond re-opening the same draft, and hand-off succeeds even when the
user turns out to own no vendor namespace — the admin app is where that is
explained.

## Operational Endpoints

```http
GET  /v1/health          # liveness and readiness, including catalog revision
POST /v1/admin/ingest    # manual re-ingest trigger (operator credentials)
POST /v1/webhooks/github # push notification from ColdCrabby/presets
```

`/health` reports the served revision and the time of the last successful ingest,
so a stalled catalog is visible to monitoring rather than silent.

The webhook endpoint **verifies the HMAC signature before parsing the body**.
It is a public, unauthenticated URL that triggers work, so signature verification
is the only thing standing between it and arbitrary re-ingest requests.

Readiness is false until the first successful ingest completes: an instance with
an empty catalog would otherwise serve confident, empty results.

## Error Model

Huma emits **RFC 9457 problem details** (`application/problem+json`):

```json
{
  "type": "https://cloud-presets.coldcrabby.dev/errors/validation",
  "title": "Unprocessable Entity",
  "status": 422,
  "detail": "Preset failed validation",
  "errors": [
    {
      "location": "body.params.fan_speed",
      "message": "expected a fraction between 0.0 and 1.0, got 100",
      "value": 100
    }
  ]
}
```

| Status | Used for |
| --- | --- |
| `400` | Malformed request |
| `401` | Missing, expired, or invalid session JWT |
| `403` | Valid identity, but not an owner of the target vendor namespace |
| `404` | Unknown preset or vendor |
| `409` | Stale base revision, or a cursor issued against a superseded catalog |
| `410` | Preset retired; the ID is permanently reserved |
| `422` | Preset failed schema or semantic validation |
| `429` | Rate limit exceeded |
| `502` | GitHub rejected the request or was unreachable |
| `503` | No catalog loaded yet, or the GitHub App rate limit is exhausted (with `Retry-After`) |

The distinction between `401` and `403` is load-bearing for the admin UI: an
expired JWT needs a silent refresh, while an ownership failure needs an
explanation. Collapsing both into one status would make the admin app retry
forever on a permission error.

Validation errors are always **field-scoped**, matching the shape returned by the
dry-run endpoint, so the editor can attach messages to individual inputs.

## Client Generation

The API describes itself. Huma serves the spec and an interactive reference off
the running server, under the same `/v1` mount as everything else:

| Path | What it is |
| --- | --- |
| `GET /v1/docs` | **Scalar API reference** — browse every endpoint, try calls, and download the spec |
| `GET /v1/openapi.json` | OpenAPI **3.1** (JSON) — the Angular client generator's input |
| `GET /v1/openapi.yaml` | OpenAPI 3.1 (YAML) |
| `GET /v1/openapi-3.0.json` | OpenAPI **3.0** (JSON) — a downgrade for 3.0-only generators |
| `GET /v1/openapi-3.0.yaml` | OpenAPI 3.0 (YAML) |

The public app links to `/v1/docs` from its header ("API"), so the viewer and the
spec download are discoverable without reading this document. The reference is
same-origin, so it needs no CORS configuration and stays in step with the running
build automatically.

The build also writes the OpenAPI 3.1 document to disk (`go run ./cmd/openapi`),
and both Angular apps generate their client from that file. Neither app
hand-writes request types.

Huma emits **3.1**, and not every generator supports 3.1 fully. That is why the
server also serves the auto-downgraded **3.0** document above: a 3.0-only
generator can consume `openapi-3.0.json` without a separate downgrade step in the
build.

The generated client is committed, so a spec change shows up as a reviewable diff
in the frontends rather than as an invisible build-time difference.
